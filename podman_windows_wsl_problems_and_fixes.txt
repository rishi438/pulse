5. ADMINER COULD NOT CONNECT TO POSTGRES BY CONTAINER NAME
============================================================

Observed containers:
podman ps --format "table {{.Names}}\t{{.Networks}}\t{{.Ports}}"

NAMES                  NETWORKS    PORTS
goofy_hodgkin          podman      0.0.0.0:5432->5432/tcp
mystifying_goldwasser  podman      0.0.0.0:8086->8080/tcp

At first this looked like both were on the same network, which was true.
But the default "podman" network had DNS disabled.

Connectivity test from Adminer:
podman exec mystifying_goldwasser php -r "var_dump(@fsockopen('goofy_hodgkin',5432));"

Confirmed result:
bool(false)

DNS check:
podman network inspect podman --format "{{.DNSEnabled}}"

Confirmed result:
false

FIX:
Attach both containers to pgnet because pgnet has DNS enabled.

Commands:
podman network connect pgnet goofy_hodgkin
podman network connect pgnet mystifying_goldwasser

Verify:
podman ps --format "table {{.Names}}\t{{.Networks}}"

DNS test:
podman exec mystifying_goldwasser getent hosts goofy_hodgkin

TCP test:
podman exec mystifying_goldwasser php -r "var_dump(@fsockopen('goofy_hodgkin',5432));"

Expected:
resource(...) of type (stream)

Adminer Server field should then be:
goofy_hodgkin

or:
goofy_hodgkin:5432

Do NOT use:
localhost

Reason:
Inside the Adminer container, localhost means the Adminer container itself.

6. PGNET EXISTED BUT NETAVARK / NFTABLES FAILED
============================================================

Observed error:
netavark (exit code 1): nftables error:
"nft" did not return successfully while applying ruleset

This happened even with:
podman run --rm --network pgnet alpine echo hello

Meaning:
The failure was not PostgreSQL-specific.
The failure was in Podman/Netavark networking inside the Podman Linux VM.

Attempted:
podman network reload --all

Result:
Error: cannot use command "podman network reload" with the remote podman client

Reason:
On Windows, PowerShell Podman is a remote client talking to the Linux Podman machine.
Some network-reload operations are not available through the remote client.

Useful VM entry:
podman machine ssh

Useful inspection inside VM:
sudo nft list ruleset
nft --version
podman --version
netavark --version

One safe restart sequence tried:
podman machine stop
wsl --shutdown
podman machine start

Important:
We intentionally avoided blindly flushing nftables rules after realizing that could disrupt firewall/network state.

============================================================

Observed .wslconfig:

This was already correct for normal WSL localhost forwarding.

9. PODMAN USER-MODE NETWORKING
============================================================

At one point Podman startup showed:
Starting user-mode networking...

We tried:
podman machine set --user-mode-networking=true

This introduced an extra Podman user-mode networking path.

Later recommendation:
Return to normal WSL networking:
podman machine stop
podman machine set --user-mode-networking=false
wsl --shutdown
podman machine start

A possible helper distro to check:

If a leftover helper distro named:
podman-net-usermode

exists, it may be a helper used for user-mode networking.

Important warning:
Do NOT unregister podman-machine-default because that is the actual Podman machine/data VM.

10. WORKING LOCALHOST FIX: NETSH PORTPROXY
============================================================

Because:
http://172.27.125.207:8086/ worked
but:
http://localhost:8086/ did not

The confirmed working workaround was Windows netsh portproxy.

Run PowerShell as Administrator:

netsh interface portproxy add v4tov4 `
  listenaddress=127.0.0.1 `
  listenport=8086 `
  connectaddress=172.27.125.207 `
  connectport=8086

Check:
netsh interface portproxy show all

Then:
http://localhost:8086

CONFIRMED:
This workaround worked.

Why use 127.0.0.1 instead of 0.0.0.0?
127.0.0.1 = local machine only
0.0.0.0   = may listen on additional host interfaces

Limitation:
The WSL/Podman VM IP (172.27.125.207) can change after restart.
If it changes, the portproxy rule must be updated.

Also:
One portproxy rule is needed per host port if the automatic localhost forwarding remains broken.

Examples:
5432 -> PostgreSQL
8086 -> Adminer
3000 -> application


============================================================
11. VIEW / DELETE PORTPROXY RULES
============================================================

Show all rules:
netsh interface portproxy show all

Delete one rule:
netsh interface portproxy delete v4tov4 `
  listenaddress=127.0.0.1 `
  listenport=8086

Example to recreate with a new WSL IP:
netsh interface portproxy add v4tov4 `
  listenaddress=127.0.0.1 `
  listenport=8086 `
  connectaddress=<CURRENT_WSL_IP> `
  connectport=8086

16. MOST IMPORTANT FINAL FIXES
============================================================

A. Adminer -> PostgreSQL
Problem:
Adminer could not connect using localhost or PostgreSQL container name.

Root cause:
Default Podman network had DNS disabled.

Fix:
podman network connect pgnet goofy_hodgkin
podman network connect pgnet mystifying_goldwasser

Adminer Server:
goofy_hodgkin


B. Windows -> Adminer localhost
Problem:
Podman published 8086, direct VM IP worked, localhost did not.

Confirmed working fix:
netsh interface portproxy add v4tov4 `
  listenaddress=127.0.0.1 `
  listenport=8086 `
  connectaddress=172.27.125.207 `
  connectport=8086


C. Mirrored WSL networking
Problem:
networkingMode=mirrored caused WSL startup/network configuration failure.

Fix:
Remove networkingMode=mirrored from .wslconfig.


D. Netavark/nftables
Problem:
Containers on pgnet initially failed to start because Netavark could not apply nftables rules.

Useful recovery:
podman machine stop
wsl --shutdown
podman machine start

If it returns, inspect from:
podman machine ssh
sudo nft list ruleset

============================================================
18. NOTE ABOUT WHAT WAS CONFIRMED VS ATTEMPTED
============================================================

CONFIRMED:
- PostgreSQL was reachable on Windows localhost:5432.
- Adminer container was running and port was published.
- Adminer worked when accessed through the Podman VM IP.
- Default "podman" network had DNSEnabled=false.
- pgnet had dns_enabled=true.
- Adminer -> goofy_hodgkin test returned bool(false) before pgnet attachment.
- netsh portproxy fixed Windows localhost access.
- networkingMode=mirrored broke WSL startup in this environment.

ATTEMPTED / NOT RELIED ON AS FINAL FIX:
- podman network reload --all from Windows remote client (unsupported).
- user-mode networking changes.
- mirrored WSL networking.
- normal localhostForwarding alone did not solve the issue in this setup.
